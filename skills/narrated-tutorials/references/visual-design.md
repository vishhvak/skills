# Choose the representation before compiling

A valid `scenes` array is not a complete visual design. Its default renderer provides boxes, labels, straight connectors and cue highlights. It cannot express the custom file panels, traveling path sheen, changing counters, locally deformed contours or stateful interactions found in the animated-diagrams studies.

When the request asks for that level of visual craft, read the installed `animated-diagrams` skill and inspect the relevant source example before authoring the lesson. Use a section `diagram` module for the result. Basic `scenes` remain useful for an intentionally simple schematic; they are not a cheaper equivalent of an authored scene.

## Plan each visual family

Record a compact table in the project: section, teaching claim, representation, visible state change, interaction if any, aligned cue words, and chosen implementation example. Choose shape and motion from the subject:

| Teaching claim | Representation that can show it |
| --- | --- |
| Where repository data comes from | A file tree with evidence/runtime panels and a visible handoff; tree connectors mean containment only |
| A move reserves a destination while holding its origin | A spatial board with distinct occupancy and reservation states, then an arrival handoff |
| A shield absorbs part of a hit | A numerical pipeline with changing values and a shield/health meter |
| A catalog changes under a policy | Keyed table rows, counts and switches that visibly settle after delivery |
| A comparison is just two facts | Two concise labels/cards; additional animation may add nothing |

Different titles on the same chain of rectangles do not make different representations. A claim about movement, transfer or mutation needs the relevant object to move, transfer or mutate; a yellow border changing targets often only repeats the narration.

For a requested reference style, carry over its composition and motion mechanisms, not its unrelated data or incidental labels. In the Kit-style examples, that includes compact monospaced text, neutral near-black surfaces, restrained outlines, path-bound packets, local sheen and separate charge/launch/impact/settle phases. Preserve the user's chosen visual style for other requests.

## Prove one section inside the player

Before batch-generating the rest of a course, compile one representative section with real narration and the intended renderer. Inspect the visual stage at its actual desktop size, during motion and while paused. Compare it with the chosen example using the same displayed scale. Check typography, unused space, label density, the object doing the teaching, and transition timing.

If the representative section still looks like the rejected generic diagram, change the representation or renderer before multiplying it across the course. Overlap checks, scene counts and successful cue validation cannot answer this design question.

Use `diagram` when the module route is required; a compile or load failure must stay visible instead of silently reverting to basic boxes. Document explicitly which sections use basic schematics by design and which use authored modules. The runtime contract and copying rules are in [diagram-modules.md](diagram-modules.md).
